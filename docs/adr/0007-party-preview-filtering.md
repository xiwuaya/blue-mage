# 悬停预览的过滤口径：「应用该配置」跟随分类过滤，「设为我」永远展示全部

多人模式弹窗里的两个悬停预览共用同一个面板，但技能列表的口径**刻意不同**：

| 触发点 | 列表内容 | 是否受「分类过滤」影响 |
| --- | --- | --- |
| 「设为我」（用户预览） | 该用户数据（文本框 / 存档）里出现过的全部未掌握技能 | **否**，有多少列多少 |
| 「应用该配置」（队伍预览） | 该队伍中至少一人未掌握、且处于当前启用分类内的技能 | **是**，与组队算法同一口径 |

队伍预览的其他规则不变：

- 候选是队伍成员未掌握技能的**并集**：只要有一名成员没掌握就列出，
  不要求全员都未掌握；
- 每项末尾的「N人」表示该队伍内有几个成员未掌握它、可以一起学习；
- 队伍成员即使被其他配置暂时隐藏，仍按其数据统计（队伍组成不随显隐状态改变）；
- 排序跟随「按未掌握人数排序」开关。

**为什么值得记下来。** 这是一个看起来像 bug 的不对称设计，而且已经被「顺手统一」
过一次：2026-11-10（`ef53324`）曾把队伍预览改成不过滤，理由是与用户预览保持一致；
2026-11-23 按使用者要求回调。**不要再次把两者的过滤口径统一。**

**队伍预览为什么必须跟随分类过滤。** 它解释的是「在当前筛选下，应用这个配置意味着
什么」：行内的「共可学习 X 个技能」、最优队伍构成、多队伍组合推荐，都以
`validSpellNos` 为口径统计。预览若列出被过滤掉的技能，就会出现「行内说 2 个、
悬浮窗列出 5 个」的矛盾，还会推荐当前视图里根本不展示的技能。为此
`buildTeamPreview` 与 `buildAlgoInputData` 共用同一个 `validSpellNos` computed，
避免两处各写一份、日后漂移。

**用户预览为什么不跟随过滤。** 它是对单个用户数据的检视：用来核对粘贴 / 编辑的
未掌握编号串是否完整，与主界面当前展示哪些学习途径无关。用户关掉某类途径
（比如只想看副本）并不代表他想在核对自己的存档时看不到其他技能。过滤掉编号会让
这份预览失去「数据核对」的用途。

**考虑过并否掉的方案：**

- **两者都跟随过滤（统一）。** 用户预览会在关闭分类时静默吞掉数据里的编号，
  无法用来核对数据。
- **两者都不跟随过滤（统一）。** 队伍预览会与同一行的「共可学习 X 个技能」
  以及推荐结果矛盾，见上。
- **在预览面板上加一个过滤开关。** 面板是悬停即走的轻量信息，加交互控件反而
  增加理解成本；两个入口的语义本就不同，不需要用户每次悬停后自己调口径。

**实现锚点（`src/components/PartyModal.vue`）：**

- `validSpellNos`：当前分类过滤下的有效技能编号，与 `buildAlgoInputData` 共用；
- `buildTeamPreview()`：队伍预览，循环内先按 `validSpellNos` 过滤；
- `previewData()` 的用户分支 / `parsePreviewList()`：用户预览，不过滤。

**回归验证。** 关闭全部分类后：悬停「设为我」仍应列出该用户全部未掌握技能；
悬停「应用该配置」应显示「当前分类过滤下没有可显示的未掌握技能」。
