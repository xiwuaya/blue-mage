# 地图名 → map key 用构建时静态表 + 库自带 getRegion() 兜底，不用 XIVAPI

打开地图需要先把中文地图名（如「中拉诺西亚」）换成 Waking Sands 的 map key（`15`）。
最初的设计是运行时调 XIVAPI 中文镜像反查 `Map.row_id`。实现时发现地图库自己就带着这份数据：
`getRegion()` 返回 `region.json`，里面有 `maps[].name → key` 的完整索引，
而且 `create()` 初始化时**本来就会拉取它**（拿不到这份数据地图根本建不起来）。

于是改成：构建时用 XIVAPI 生成 `tools/map-keys.json` 静态表（`tools/update-map-keys.js`，
接在 `prebuild` 上），运行时先查静态表，未命中才用已经加载好的 `getRegion()` 兜底。
**运行时一次 XIVAPI 都不调。**

**为什么值得记下来。** 代码里凭空多出一个 `tools/map-keys.json`、一个构建脚本，
还多了一条"查不到就回退到库索引"的路径——不知道这段历史的人会以为在重复造轮子。

**为什么不直接用 getRegion() 就好。** 该文件 1073 条记录里有 534 条重名，
即使过滤掉子区域（`subName` 非空）和占位条目（`id` 以 `default/`、`region/` 开头），
`摩杜纳` 仍有 3 个候选（key 25 / 91 / 105）。静态表可以在构建时人工核对，
比运行时的启发式规则可靠。

**考虑过并否掉的方案：**

- **纯运行时 XIVAPI**：每次首点都有网络延迟，且依赖第三方接口可用性。CORS 确实可用
  （实测 `Access-Control-Allow-Origin: *`），但没必要为一个 31 条的静态数据集付这个代价。
- **纯 getRegion()，不要静态表**：省掉构建步骤，但重名消歧只能靠启发式（取最小 key）。
  实测该规则与 XIVAPI 判定一致，但那是 31 个样本上的巧合，不足以为它背书。

**交叉验证。** 两个独立数据源（XIVAPI `Map.row_id` 与 `region.json` 的 `key`）
在当前全部 30 个可解析地名上**结果完全一致，0 处分歧**，说明 key 空间是可靠的。
第 31 个地名（`库尔札斯西部高地`）两个源都查不到，因为 `spells.json` 里写成了 `库尔扎斯`
（`扎` 而非 `札`）——已修正，构建脚本会对解析失败的地名报警。
