# FATE 刷新位置地图 · 开发记录

[PR #2](https://github.com/xiwuaya/blue-mage/pull/2) 基于 [任务接取与狩猎地图](../任务接取与狩猎地图/开发记录.md)。本次逐项核对了 27 条 FATE 学习途径，对应 26 个独立事件，补齐原先缺坐标的 8 个事件。已收录的每个事件各有一个可核实的中心点；这一数量反映来源的覆盖范围，不能据此断定事件只会在一个地点刷新。

## spells.json 的迁移与新途径写法

原格式把事件单点写在每一条 `method[].position` 中。本次移除了已登记 FATE 途径中的重复坐标，把位置集中到 `tools/data/fate-spawns.json`。同一事件关联多个技能时，各技能仍分别填写所学怪物与等级，共用事件的所有位置。下面两段是同一事件在两个文件中的对应记录。

`tools/data/spells.json` → 技能的 `method` 数组元素（省略可选颜色）：

```json
{
  "type": "fate",
  "level": 46,
  "map": "北萨纳兰",
  "name": "逆向工程",
  "mob": "废弃的魔导先锋"
}
```

`tools/data/fate-spawns.json` → 以事件名为键的记录：

```json
{
  "逆向工程": {
    "id": 457,
    "map": "北萨纳兰",
    "positions": [[18.92, 16.09]]
  }
}
```

| 位置 | 必填项 | 填写条件与用途 |
| --- | --- | --- |
| 每条 FATE 途径 | `type: "fate"`、`level`（数字）、`map`、`name`、`mob` | `name` 是事件，`mob` 是传授技能的目标，可能不同。可选 `note`、`color`。 |
| 每个新事件的共享记录 | 事件名键、`id`（国服 Fate 数字行号）、`map`、`positions` | 已登记的同一事件直接复用。键名和地图名须分别与途径的 `name`、`map` 完全一致。每个发布的事件至少有一个数值坐标对。 |
| 单点或多点 | `positions[0]` 为事件中心 | 固定单点用 `[[X,Y]]`。有额外点位证据时，在数组末尾继续追加 `[X,Y]`。地图同时标出全部点。 |
| 旧格式兼容 | 无新增必填项 | 读取不到同名同图记录时，前端、静态详情入口可回退到途径原有的单点 `position`。这仅用于兼容，新事件须登记共享表才能通过同步检查。 |

任务 NPC 仍使用 `questStart.position`，野怪仍使用途径上的 `position`，狩猎多点仍在 `hunt-spawns.json`。完整的 12 类途径必填字段与 CSV 导入限制见[途径填写表](../任务接取与狩猎地图/开发记录.md#新增学习途径时怎样填写-spellsjson)。

## 数据从哪里来，怎样刷新

1. **确认身份。** 以学习途径的中文事件名查国服 Fate 表，核对游戏行号与地图。简称、破折号、连锁事件阶段容易相似；先确认具体事件，再用其行号取坐标。共享表的键沿用项目里途径的名称。[国服 Fate.csv 快照](https://github.com/thewakingsands/ffxiv-datamining-cn/blob/ae29be8b21a32329e3356709422427540bf7e364/Fate.csv)
2. **准备两张表。** 给 `spells.json` 加入途径。新事件先在共享表登记 `id`、`map`、`positions: []`，空数组仅用于首次同步前。新地图先运行 `node tools/update/update-map-keys.js`，核对 `tools/data/map-keys.json` 的中文名与 Map 编号。
3. **更新事件中心。** 将 Teamcraft 的完整 `fates.json` 下载到本地，从项目根目录执行下列命令。脚本按 ID 读取 `position.x/y`，检查 `position.map` 和本地地图编号相等，再写入首个坐标对。日常构建直接使用提交的共享表。刷新数据时在变更记录注明所用快照。[本次 Teamcraft 坐标快照](https://github.com/ffxiv-teamcraft/ffxiv-teamcraft/blob/cb9eede14f45cd16b4ee229e7a80e624a44c0209/libs/data/src/lib/json/fates.json)

   ```sh
   node tools/update/sync-fate-spawns.js /path/to/fates.json
   git diff -- tools/data/fate-spawns.json tools/data/map-keys.json tools/data/spells.json
   ```

4. **核对额外点。** Teamcraft 每个事件只提供一个中心。确认同一事件在另一个地点出现后，将游戏内 X、Y 加到 `positions[1]` 及之后，并在 `tools/README.md` 的 FATE 小节记下证据。同步会保留附加点并剔除完全相同的坐标；同一中心的取整差异须人工辨别。若报告缺事件、缺有效中心或地图编号不符，先核对事件 ID、译名及地图；所有记录检查完毕后脚本才写文件。

## 代码与旧实现的取舍

| 文件 | 改动与理由 |
| --- | --- |
| `src/lib/spell.ts`、`src/components/Method.vue`、`tools/pagegen/spell-page-template.js` | 让 FATE 使用已有的多点地图，列表和静态详情页按相同名称、地图解析坐标。详情页深链进入选定途径。 |
| `tools/update/sync-fate-spawns.js`、`tools/update/update-map-keys.js` | 前者用本地快照核验全部 FATE 途径并刷新事件中心；后者将 FATE 所在地图纳入地名解析。 |
| `tools/update/update-fate-positions.js`、`tools/data/fate-positions.json` | 删除旧 Garland 单点脚本及缓存。旧流程用中文名匹配 ID，只能补写单条途径缺失的坐标，且仍有事件无结果。新的共享表同时覆盖完整性检查和多点维护。 |
| `package.json`、`.github/workflows/publish-to-pages.yml`、`tools/README.md` | 移除 prebuild 的旧采集步骤，清理发布流程中关于旧缓存的说明，记录按需更新命令。 |
| `src/components/MapButton.vue`、`Method.vue`、`SpellItem.vue` | 任务、野怪、狩猎、FATE 共用图标入口。悬停或键盘聚焦时预览名称、地图和坐标；多点预览最多列三个并给出总数，点击后打开完整地图。 |
| `src/App.vue`、`Progress.vue`、`SpellList.vue`、`SpellItem.vue`、`Method.vue`、`src/lib/spell.ts` | 增加“显示主线副本的解锁途径”，默认关闭并保存选择。主列表用它控制主线解锁地图图标；详情页深链仍可打开地图。组件文件均在 `src/components/`，App 位于 `src/`。 |
| `tools/data/duty-unlocks.json`、`tools/verify/verify-hydration.mjs` | 给 40 个由主线任务开放的内容加标记，覆盖 59 条途径。浏览器回归覆盖各类图标、悬浮预览、点击开图与主线开关持久化。 |

**今后新增副本的分类规则。** 按开放任务自身的 `questId` 对照国服 ScenarioTree 行号。属于主线时，在对应的 `duty-unlocks.json` 记录里增加布尔值 `"mainScenario": true`。支线和对话解锁省略该字段。仅有前置主线要求、实际由支线开放的副本按支线处理。同名内容的不同难度要分别匹配；各技能的 `spells.json` 无需重复写分类。[本次分类使用的 ScenarioTree.csv](https://github.com/thewakingsands/ffxiv-datamining-cn/blob/ae29be8b21a32329e3356709422427540bf7e364/ScenarioTree.csv)

## 提交前如何验收

在项目根目录运行 `yarn build` 和 `yarn verify:hydration`。打开“逆向工程”途径，核对悬停预览与地图弹窗的坐标相同；再从静态详情页打开该途径。更新多点数据时，核对弹窗标记数、坐标列表和初始视野；测试用点不要提交到正式数据。改动深链或发布路径时运行 `yarn build:subpath` 并检查子路径入口。改动副本分类时，用一条主线和一条支线分别检查默认状态、勾选后、刷新后、取消勾选后的图标。
