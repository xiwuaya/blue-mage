## 结论与 Phase 3/4 依据

1. **N ≤ 12 完全可用**：N=12/M=3 仅 6.7ms，接 UI 无压力；N=15/M=3 约 0.8s，已接近交互式体验上限。
2. **N=18/M=3 baseline 不可行**：按已观测速率（~2M 节点/s）与理论节点总量（约 1.7×10⁹，各层状态数之和）估算，跑完全量需 **15 分钟量级**；瓶颈确如文档 §47 所述在 DFS 分组搜索，而非 C(N,M)=816 的预计算。
3. 优化路线建议维持文档 §49 顺序：Phase 3 `teamMasksByUser` 将每层候选扫描从 O(C(N,M)) 降到 O(C(N−1,M−1))（N=18 时 816→136，约 6 倍）；若仍不够，Phase 4 加「剩余总分上界剪枝」（当前分支理论最大增量 ≤ 剩余队伍数 × 全局最大队分）与增量统计配合，可把 N=15/18 压回实时范围。
4. **文档 §47 数表勘误**：N=18/M=3 的完整分组数实际为 **190,590,400**（= 18!/(3!⁶·6!)），文档中的 17,153,136 有误；N=6、N=12 两行无误。这不影响结论方向，但影响 N=18 的耗时预期。

## 附：手工可验证场景

用户 0/1/2 共有技能 10..14（5 个），用户 3/4/5 共有技能 20..26（7 个），两组技能互不重叠：

```
最优解唯一：Team1=[0,1,2] 真实共同技能 5；Team2=[3,4,5] 真实共同技能 7
effectiveTotal = 5 + 7 = 12（未触顶）
varianceScore = 2·(5² + 7²) − 12² = 4
```
