# Blue Mage「最优组队算法」优化开发文档

> **文档用途：**作为后续实际修改 `PartyModal.vue` 的实现依据。  
> **当前阶段：**需求与算法设计阶段，尚未修改代码。  
> **核心目标：**从原本“寻找一个共同技能最多的 M 人队伍”，升级为“将所有符合条件的玩家尽可能划分为多个 M 人队伍，并在共同技能总量、均衡程度等多个目标之间进行优化”。

---

# 1. 项目背景

当前 `PartyModal.vue` 中存在一个：

```ts
const bestParty = computed(() => {
    ...
})
```

原算法主要目标是：

> 从当前参与玩家中找出一个固定人数 `M` 的队伍，使该队伍拥有的共同技能数量最大。

现需要将其升级为：

> **一次性寻找整个玩家集合的最优组队方案。**

例如：

```text
N = 12
M = 3

原算法：
12 人 → 找 1 个最优 3 人队

新算法：
12 人 → 划分成 4 个 3 人队
       → 评价整个 4 队方案
       → 找出整体最优方案
```

---

# 2. 基本概念

## 2.1 Active User

参与算法的用户称为 `activeUsers`。

对应现有代码中的：

```ts
visibilityState !== 2
```

也就是说：

| visibilityState | 含义     | 是否进入算法 |
| --------------- | -------- | ------------ |
| `0`             | 普通用户 | ✅            |
| `1`             | 必须参加 | ✅            |
| `2`             | 隐藏用户 | ❌            |

隐藏用户完全从算法中排除。

---

# 3. 用户索引

算法内部使用 `activeUsers` 的连续索引：

```text
activeIndex
0
1
2
...
N-1
```

而不是直接使用 `originalIndex`。

例如：

```text
原始用户：
user1      → originalIndex = 0
teammate1  → originalIndex = 1
teammate2  → originalIndex = 2
...

隐藏 user 被删除后：

activeUsers：
0 → user1
1 → teammate2
2 → teammate4
...
```

## 原因

BitMask 使用：

```ts
number
```

因此必须保证参与位运算的索引连续。

`originalIndex` 只负责最终映射回 UI 用户。

# 4. BitMask 方案

已经确定：

> 使用普通 JavaScript `number` 作为 BitMask。

并明确限制：

```text
N ≤ 30
```

不使用 `BigInt`。

例如：

```text
用户 0、2、4：

00101
```

可以表示为：

```ts
1 << 0
1 << 2
1 << 4
```

组合：

```ts
0b10101
```

# 5. 队伍人数 M

`targetM` 表示每支队伍的人数。

当前 UI 最大值为：

```text
M ≤ 8
```

现阶段仍沿用现有 UI 限制。

算法层面：

```text
N ≤ 30
```

是 BitMask 的明确约束。

# 6. 完整分组目标

设：

```text
N = active user 数量
M = 每队人数
```

完整队伍数量：

```ts
teamCount = Math.floor(N / M)
```

需要排除的人数：

```ts
excludedCount = N % M
```

例如：

```text
N = 10
M = 3

teamCount = 3
excludedCount = 1
```

最终：

```text
Team 1 → 3 人
Team 2 → 3 人
Team 3 → 3 人
Excluded → 1 人
```

---

# 7. 排除用户规则

当：

```text
N % M !== 0
```

时，无法让所有用户都进入完整队伍。

因此：

> **必须恰好排除 `N % M` 个用户。**

并且：

> **只有 `visibilityState === 0` 的普通用户可以被排除。**

`visibilityState === 1` 的必须参加用户绝对不能被排除。

# 8. Must Include 约束

现有：

```ts
mustIncludeMask
```

继续使用。

其中：

```text
visibilityState === 1
```

的 active user 对应位被设置为 `1`。

例如：

```text
activeUsers = 0 1 2 3 4 5

must include：
1、4

mustIncludeMask：

010010
```

# 9. Must Include 的重要变化

原算法存在类似：

```ts
if (mustIncludeCount > targetM) {
    return null;
}
```

这种限制。

**新算法必须删除这种逻辑。**

原因：

假设：

```text
M = 3
mustInclude = 4 人
```

并不意味着无解。

例如：

```text
Team 1 → must A + must B + normal
Team 2 → must C + must D + normal
```

完全合法。

因此：

> `mustInclude` 是**整个分组方案的约束**，不是“单支队伍必须包含的人员”。

# 10. 基本可行性检查

进入 DFS 前进行基础检查。

至少包括：

### 10.1 人数不足

```text
N < M
```

则无法组成任何完整队伍。

返回无解。

---

### 10.2 Must Include 数量

必须满足：

```text
mustIncludeCount ≤ teamCount × M
```

否则必须参加人数超过所有队伍的总席位。

---

### 10.3 排除人数

需要：

```text
normalUserCount ≥ excludedCount
```

因为只有普通用户可以被排除。




因此这个队伍拥有技能 100。

# 13. TeamScore

为每一个 M 人组合计算一次团队评分。

定义：

```ts
type TeamScore = {
    commonSkillCount: number;
    effectiveCommonSkillCount: number;
};
```

其中：

### `commonSkillCount`

真实共同技能数量。

用于：

- UI 显示
- 最终结果记录

---

### `effectiveCommonSkillCount`

算法使用的有效共同技能数量：

```ts
effectiveCommonSkillCount =
    Math.min(commonSkillCount, MAX_EFFECTIVE_COMMON_SKILLS)
```

其中：

```ts
MAX_EFFECTIVE_COMMON_SKILLS = 12;
```

---

# 14. 为什么设置 12 上限

这是一个**业务领域约束**，不是单纯数学优化。

蓝魔法组队场景下：

> 一个队伍实际能利用的共同技能数量达到一定程度后，再继续增加共同技能，对组队价值的提升不再继续按照线性方式增加。

因此：

```text
真实共同技能：

5  → effective = 5
8  → effective = 8
12 → effective = 12
15 → effective = 12
20 → effective = 12
```

---

# 15. 算法评分必须使用 Effective Count

已经明确：

> **总共同技能数量使用 capped/effective count。**

即：

```ts
effectiveTotalCommonSkills =
    Σ team.effectiveCommonSkillCount
```

而不是：

```ts
Σ team.commonSkillCount
```

# 18. TeamScore 预计算

已经确定：

> **预先计算全部 `C(N,M)` 个 M 人组合。**

而不是 DFS 遇到某个团队时才计算。

流程：

```text
N
↓
generateCombinationMasks(N, M)
↓
得到所有 M 人 BitMask
↓
calculateTeamScore()
↓
teamScoreMap
```

---

# 19. 重要约束：预计算不能使用 mustInclude

生成团队评分时：

```text
必须计算所有 M 人组合
```

**不能因为某个组合不包含所有 mustInclude 用户而跳过它。**

例如：

```text
M = 3

mustInclude = {0,1,2,3}
```

团队：

```text
{0,1,4}
```

虽然没有包含全部 mustInclude，但它仍然可能是最终合法分组中的一个队伍。

例如：

```text
Team 1 → {0,1,4}
Team 2 → {2,3,5}
```

所以：

> `mustIncludeMask` 属于 DFS 的**分组约束**，不能进入 `TeamScore` 的定义。

# 24. DFS 分组算法

完整分组采用：

> **DFS / Backtracking**

目标：

```text
把 activeUsers 划分为：

teamCount 个 M 人团队

以及：

excludedCount 个被排除用户
```

---

# 25. 防止队伍排列重复

已经确定：

> 每次 DFS 创建的新队伍，必须包含“剩余用户中索引最小的用户”。

例如：

```text
剩余：

0 1 2 3 4 5
```

下一队必须包含：

```text
0
```

因此：

```text
[0,1,2] + [3,4,5]
```

会被探索。

但：

```text
[3,4,5] + [0,1,2]
```

不会再次探索。

---

# 26. 这样可以消除什么重复

如果不加这个规则：

```text
ABC + DEF
```

和：

```text
DEF + ABC
```

会被认为是两条 DFS 路径。

实际上它们是同一个分组。

最小剩余用户规则可以消除这种**队伍排列导致的重复**。

并维护：

# 33. 优化目标

最终分组不是单纯比较：

```text
共同技能总数
```

而是多级排序。

优先级已经确定：

```text
第一优先级：
最大化 effectiveTotalCommonSkills

第二优先级：
最小化 effective team count 的方差

第三优先级：
Team userIndices 字典序最小

第四优先级：
Excluded userIndices 字典序最小
```

---

# 34. 第一优先级：总有效共同技能

例如：

```text
方案 A：

Team 1 = 12
Team 2 = 10
Team 3 = 8

总和 = 30
```

```text
方案 B：

Team 1 = 11
Team 2 = 11
Team 3 = 8

总和 = 30
```

两者：

```text
30 = 30
```

所以进入第二优先级。

---

# 35. 第二优先级：均衡程度

已经确定：

> 使用**方差**衡量团队之间的均衡程度。

但实际代码不需要进行浮点除法。

假设：

```text
x1, x2, ..., xT
```

其中：

```text
xi = effectiveCommonSkillCount
```

总体方差：

\[
Variance =
\frac{1}{T}\sum x_i^2
-
\left(\frac{1}{T}\sum x_i\right)^2
\]

为了避免浮点计算，使用：

\[
varianceScore =
T\sum x_i^2-(\sum x_i)^2
\]

比较时：

```text
varianceScore 越小越好
```

这与比较真实方差完全等价。

---

# 36. 方差必须使用 Effective Count

已经确定：

> 方差同样基于 capped/effective count。

例如：

```text
实际：
15 / 12 / 8
```

算法实际使用：

```text
12 / 12 / 8
```

而不是：

```text
15 / 12 / 8
```

这样总分和均衡评价使用的是同一套业务定义。

---

# 37. 第三优先级：Team Lexicographic

如果：

```text
总有效共同技能相同
```

并且：

```text
varianceScore 相同
```

则比较团队用户索引。

每个团队内部：

```text
userIndices ascending
```

例如：

```text
[0, 2, 5]
```

而不是：

```text
[5, 0, 2]
```

---

# 38. Team 顺序

团队按照第一个用户索引排序。

由于 DFS 每次选择剩余最小用户，因此实际上可以天然形成：

```text
[
    [0,...],
    [1/...],
    [3,...]
]
```

这样的规范顺序。

最终仍应进行明确的 lexicographic comparison。

---

# 39. Team Lexicographic 示例

例如：

```text
方案 A：
[
    [0,1,5],
    [2,3,4]
]
```

方案 B：

```text
[
    [0,2,3],
    [1,4,5]
]
```

比较：

```text
第一队：
[0,1,5]
[0,2,3]
```

因为：

```text
1 < 2
```

所以方案 A 更优。

---

# 40. 第四优先级：Excluded Lexicographic

只有前三项完全相同，才比较排除用户。

例如：

```text
方案 A：
excluded = [4,7]

方案 B：
excluded = [5,6]
```

因为：

```text
4 < 5
```

所以 A 更优。

Excluded 列表始终升序排列。

```text
N % M === 0
```

完整分组数量：

\[
\frac{N!}
{(M!)^{N/M}(N/M)!}
\]

例如 M=3：

|    N | 完整分组数量 |
| ---: | -----------: |
|    6 |           10 |
|   12 |       15,400 |
|   18 |   17,153,136 |

这说明：

> N 增大后，真正的性能瓶颈将主要来自 DFS 分组搜索，而不是 M 人组合预计算。

---

# 48. M 人组合数量

团队预计算数量：

\[
C(N,M)
\]

例如：

|    N |    M | Team Combination |
| ---: | ---: | ---------------: |
|    6 |    3 |               20 |
|   12 |    3 |              220 |
|   18 |    3 |              816 |

因此：

```text
TeamScore 预计算
```

本身通常不是主要问题。
